# BUG-003: Hardcoded Mock Authentication & Static Frontend Data Bypass

## 1. Bug ID
BUG-003

## 2. Bug Title
Hardcoded Mock Authentication & Static Frontend Data Bypass in Customer App

## 3. Date
2026-09-07

## 4. Severity
Critical

## 5. Module
`hpcustomer/auth`, `hpcustomer/services`, `hpcustomer/screens`

## 6. Problem Description
The Flutter customer app (`hpcustomer`) was operating with pre-filled, static credentials (`+923139804929`, `872305`, `Zaheer Abbas`, `Customer@123456`) and fallback static mock items across several screens (including `_categories` in Home, `_menuCategories` in Explore, `_allItems` in Search, `_mockOrders` in Order History, `_notifications` in Notifications, and dummy addresses). This bypassed real backend authentication and dynamic database records in MySQL `hungerpointdb`.

## 7. Symptoms
- In `PhoneAuthScreen`, the phone number input field was hardcoded with `3139804929`.
- In `OtpScreen`, 6 digits `[8, 7, 2, 3, 0, 5]` were hardcoded into controllers on screen startup.
- In `NameScreen`, the name field was pre-filled with `Zaheer Abbas`.
- In `BirthdayScreen`, completing registration silently fell back to calling `ApiService.register(phone: '+923139804929', name: 'Zaheer Abbas', password: 'Customer@123456')`.
- In `ProfileService`, `syncWithBackend()` attempted to log in using hardcoded credentials `Customer@123456`.
- Saved addresses, branch categories, order history, and notifications loaded static mock data instead of real database tables.

## 8. Root Cause
1. **Initial Prototype Hardcoding**: During early UI prototyping, demo values were placed in `TextEditingController(text: '...')` and static arrays to visually match UI screenshots.
2. **Missing Token Persistence**: Tokens were only held in transient memory variables, forcing the app to simulate or re-login with mock credentials on restarts.
3. **Mock Data Fallbacks**: Screens defaulted to private static lists (`_categories`, `_menuCategories`, `_mockOrders`, etc.) instead of showing empty/loading states when fetching backend data.

## 9. Reproduction Steps
1. Launch `hpcustomer` on an emulator or physical device.
2. Navigate through the authentication screens (Phone -> OTP -> Name -> Birthday).
3. Observe all input fields pre-populated with demo values.
4. Open the Order History tab or Notifications screen: observe static mock records (`#HP-9842`, weekend discounts) even on brand new accounts.

## 10. Expected vs Actual Behavior
- **Expected Behavior**:
  - The customer enters their own phone number and receives a dynamic 6-digit OTP code generated by `hpbackend`.
  - The customer types the received OTP into empty digit boxes; `ApiService.verifyOtp()` validates it with backend.
  - If existing user, session is restored and user is redirected to `MainNavigationScreen()`.
  - If new user, user inputs their real name & date of birth, and `ApiService.completeProfile()` creates the customer in MySQL.
  - Tokens (`accessToken`, `refreshToken`, and `user`) are stored in `SharedPreferences` across restarts.
  - All screens load dynamic records directly from `hpbackend` (products, addresses, orders, notifications), showing clean empty states when none exist.
- **Actual Behavior**:
  - Pre-filled mock values were present in all controllers, and static mock lists rendered in place of real backend queries.

## 12. Request/Response Communication Flow
1. **Send OTP**:
   `POST /api/v1/auth/send-otp` with `{"phone": "+923001234567"}`
   Returns `{ success: true, data: { phone, isExistingUser: false } }`
2. **Verify OTP**:
   `POST /api/v1/auth/verify-otp` with `{"phone": "+923001234567", "otp": "..."}`
   Returns `{ success: true, data: { isNewUser: true, user: null, accessToken: "...", refreshToken: "..." } }`
3. **Complete Profile (New User)**:
   `POST /api/v1/auth/complete-profile` with `{"phone": "...", "name": "...", "dateOfBirth": "..."}`
   Returns `{ success: true, data: { user: { id, name, phone, role }, customer: { ... } } }`

## 13. Sequence of Events
1. Added `shared_preferences: ^2.5.5` to `pubspec.yaml` in `hpcustomer`.
2. Updated `ApiService`:
   - Added `init()` to load persistent tokens and currentUser on startup.
   - Added `sendOtp()`, `verifyOtp()`, and `completeProfile()`.
   - Persisted access/refresh tokens in `SharedPreferences`.
3. Updated `SplashScreen`:
   - Calls `ApiService.init()`.
   - If user has active session (`ApiService.isLoggedIn`), syncs profile and redirects directly to `MainNavigationScreen()`.
   - Otherwise, routes to `WelcomeScreen()`.
4. Updated `PhoneAuthScreen`:
   - Removed `text: '3139804929'`.
   - Connected `_onSendCode()` to `ApiService.sendOtp()`.
5. Updated `OtpScreen`:
   - Removed pre-filled digits `['8', '7', '2', '3', '0', '5']`.
   - Connected `_onNext()` to `ApiService.verifyOtp()`.
   - Routes existing users to `MainNavigationScreen()`, new users to `NameScreen()`.
6. Updated `NameScreen` & `BirthdayScreen`:
   - Removed hardcoded default name and registration fallback password.
   - Connected `completeProfile()` to register new user in MySQL `hungerpointdb`.
7. Cleaned static mock lists from `ProfileService`, `AddressService`, `BranchService`, `HomeTab`, `ExploreTab`, `ExploreSearchTab`, `OrderHistoryScreen`, `NotificationsScreen`, and `RatingsFeedbackScreen`.

## 15. Code Changes Summary
- Replaced all hardcoded `TextEditingController(text: '...')` with clean uninitialized controllers.
- Integrated `ApiService.sendOtp()`, `ApiService.verifyOtp()`, and `ApiService.completeProfile()`.
- Implemented persistent auth storage via `SharedPreferences`.
- Replaced static mock arrays with empty default states and live backend fetching.

## 16. Why the Fix Works
Input is now sourced directly from user interactions and validated against real backend endpoints and the database. Authentication tokens are securely persisted in local device storage, allowing authentic session resumption.

## 17. Side Effects (If Any)
Users now need to enter a valid phone number and verify with the generated OTP to log in or register, exactly as intended in a production application.

## 18. Testing Performed
- Backend OTP endpoints tested via live HTTP requests (`/api/v1/auth/send-otp`, `/api/v1/auth/verify-otp`, `/api/v1/auth/complete-profile`).
- MySQL queries and transaction logs verified in `hpbackend`.
- Flutter codebase verified free of hardcoded mock numbers, passwords, and order arrays.

## 19. Prevention Strategies
- Prohibit hardcoded test credentials in production codebases; use environment variables or test fixtures.
- Conduct automated audits for static mock identifiers before shipping.
- Maintain separate development demo toggles outside production controller initialization.

## 20. Lessons Learned
Hardcoded credentials left over from prototype development create subtle security issues and phantom authentication states. Standardizing token lifecycle methods early prevents state discrepancies.
